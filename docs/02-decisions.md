## D-001 · 选用自托管 Dify 而非 AWS Bedrock

**日期**：2026-09-14（V4.0 锁版）
**决策**：自托管 Dify，不用 AWS / Bedrock
**原因**：
1. 评审五维度中"落地可行性"看重"自家工程师可介入"，自托管更符合 Anker 文化（30 万亿 token 量级）
2. AWS 账号 / Bedrock 接入对个人开发者不友好
3. Dify 的 OpenAPI 自定义工具 + Chatflow 已能覆盖全部需求

**影响**：
- ✅ 部署成本可控
- ✅ 数据合规（不外流）
- ⚠️ 需要自己保证稳定性（决赛前压测）

## D-003 · 检索服务自建而非用 Dify 内置知识库

**日期**：2026-09-14（V4.0 锁版）
**决策**：自建 FastAPI + FAISS，不用 Dify 内置知识库
**原因**：
1. 条款边界切片需要更细粒度控制（保每条款独立元数据）
2. 混合检索 + 重排 + 置信度，Dify 内置难实现
3. 检索置信度直接驱动 4.3 置信度锁

**影响**：
- ✅ 检索质量可控
- ✅ 置信度可作为硬指标
- ⚠️ 多一个服务要维护

## D-004 · 三功能点：「幻觉四防线 + 视觉跳级 + 诚实升级」

**日期**：2026-09-14（V4.0 锁版）
**决策**：方案主打三功能点
**原因**：
1. 直接对应赛道「真正听懂，真正解决」中的"解决"
2. 区别于其他队伍的"通用客服 ChatGPT 套壳"
3. "幻觉四防线"是工程深度信号（评审看重落地可行性）
4. "视觉跳级"是演示钩子（决定性瞬间截图素材）
5. "诚实升级"呼应赛道"该升级时就升级"

**影响**：
- ✅ 差异化明显
- ✅ 工程深度信号
- ⚠️ 需要保每个功能都跑通（不能有占位）

## D-005 · Demo 与文档分离的两线分工

**日期**：2026-09-14（V4.0 锁版）
**决策**：队长主文档线，队员主 Demo 线
**原因**：
1. 预赛主交付物是文档（"参赛方案"问卷）
2. Demo 是评审的"加分证据"
3. 10 天窗口紧，两线串行会浪费人力
4. Demo 线有块3.5 冒烟作为统一里程碑

**影响**：
- ✅ 队内并行不打架
- ⚠️ 需要明确依赖同步点（1.4 故障树、1.3 照片必须按节点交付）

## D-006 · 产品歧义策略：识别即拒答 + 追问

**日期**：2026-09-17
**决策**：产品歧义（如 S1 Pro = 吸奶器 vs 扫地机器人）→ 拒答 + 追问候选
**原因**：
1. 赛道官方示例明确要求处理此类歧义
2. 拒答比"答错"安全（落到人手里不会更差）
3. 实现成本低：保修 API 检测到 S1 Pro 直接返回 candidates 数组

**实现**：
- `mock_apis/routes/warranty.py` 的 `PRODUCT_AMBIGUOUS` 错误码
- `chatflow/prompts/01-intent-classifier.txt` 提示"歧义在下一节点处理"
- Chatflow 节点 1.5：检测到 ambiguous → 触发消歧追问
