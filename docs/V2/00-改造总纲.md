## 1. 对话质量：真实回应 + 引导闭环

### 1.1 真实回应（改表达层提示词）

每条回复必须满足：

1. **先回应用户刚说的**，确认关键信息再往下走：
   > 用户：我的充电宝充不进去了
   > ✅「充不进电的话，我们先定位一下是哪种情况——」
   > ❌「是充电宝自己充不进电，还是不能给其他设备充电？」
2. **禁止原样复读**上一轮提问（已有 `ask_repeat` 标记，表达层据此换说法）。
3. **追问要说清为什么问**：半句话交代意图，让用户知道答了有什么用。
4. 始终专业、像真人在打字。**不出现机制名，不出现"系统已触发第 N 道防线"这类播报。**

### 1.2 引导闭环：每轮追问都带可点选项

**目标**：用户能点气泡，不用打字。这是本次改造的核心。

**契约 B 新增字段 `options`：**

```json
{
  "answer": "充不进电的话，先确认一下是哪种情况——",
  "state": {
    "options": [
      { "label": "充电宝自己充不进", "value": "自己" },
      { "label": "给手机充电不行",   "value": "输出" }
    ]
  }
}
```

> 注意：`options` 与 `summary` 都放在 **`state` 内部**，随现有的 `__EVIDENCE_V1__` 标记一起下发。
> 不放顶层——前端只从证据标记里取数据，多一个顶层字段就要多一条解析路径。详见 `spec/00-契约冻结.md`。

**生成规则：**

- 随当前排障节点生成，数据源就是 `engine.py` 里已有的 `TREES[node][1]`，**不需要新增知识**。
- 非追问类回复（政策、核保、安全）不带 `options`，或带 1–2 个后续动作（如「我要退货」「转人工」）。
- 选项文字用**用户的话**，不用系统的话（「不能给其他设备充电」而不是「输出」）。
- 前端渲染为**输入框上方**的「快速模拟对话」小气泡，点击等价于发送 `value`；消歧等同类追问也走这里，不再单独做大卡片。
- **必须同时保留自由打字**：用户打「给手机充不进去」也要能推进，由 `branch_answer` 归一保证。

> 一轮追问 = 一句真实回应 + 一个问题 + 若干可点选项 + 明确的下一步预期。

## 2. 左侧聊天区

### 2.1 用户气泡下方：理解辅助气泡（只给用户消息加）

```

## 3. 右侧看板：改成三层

> 现状 4 个 tab（决策与路由 / 看图跳级 / 情绪监测 / 出处检索）信息被切碎，全部拆掉重组。

### 上层 · 会话摘要 + 诉求总结

```

  用户在排查 737 充不进电问题，已确认换线无效，当前停留在屏幕反馈确认

诉求                 [排障]  [疑似硬件故障]  [可能涉及保修]
```

- **会话摘要**：一句话说清"到目前为止发生了什么、卡在哪"
  - 由 **extract 节点顺带输出 `summary` 字段**（同一轮模型调用，不加成本、不加延迟）
- **诉求总结**：诉求标签**按类型着色**
  - 配色：排障=蓝 `#38bdf8` / 核保=青 `#06b6d4` / 退货=橙 `#f59e0b` / 投诉=红 `#ef4444` / 安全=深红 `#dc2626` / 咨询=灰

### 中层 · 用户档案 + 产品信息 + 处理依据

```
用户档案                        产品信息
  用户   王先生（金卡）           型号   Anker 737
  订单   DEMO-US-001              品类   充电宝
  渠道   官网 (US)                图上   电芯 / 鼓包（置信度 0.9）
  保修   期内 · 24 个月           状态   安全熔断

处理依据（出处锁）
  · faq_anker737_f1  检查墙插、线与充电头…   🔗 官方来源
```

- **产品信息**：来自 `visionEvidence` + `state.product`（**原「看图跳级」内容并入这里**）
- **用户档案**：来自**新增的模拟用户数据**（见 4.1）
- **处理依据**：即原「出处检索」，**必须保留** —— 这是四道防线里"出处锁"唯一的可视化

### 下层 · 工单流程

```

## 9. 风险与取舍（含比赛视角）

### 9.1 最大的风险不在代码，在文档

参赛方案仍是 **V0.3 原稿**，`docs/reviews/参赛方案审核.md` 列的 10 条「必须纠正的主张」一条都没落地。
而本次改造（引导闭环、三层看板、转派动作）在方案里**找不到对应的功能点**——改完不同步文档，就是「实现第三次跑在文档前面」。

**对策**：本次改造收尾时必须产出方案 V1.0，把改造落成方案里的功能点表述；否则 demo 越好，文档与实现的落差越大。

### 9.2 演示可能「看起来像按键菜单」

可点芯片对交互是加分，但风险是 demo 退化成「点按钮走流水线」，被评委读成「决策树套了个 AI 壳」，反而伤**项目创新性**得分。

**对策**：芯片定位为**快捷方式而非唯一路径**；演示剧本必须包含**自由打字的混乱口语**输入（如「快气死我了我的737充不进去」），证明模型真的在理解而不是在匹配关键词。

### 9.3 「已转派」的表述边界

`参赛方案审核.md` 已明确：工单是 SQLite 模拟记录，未对接真实客服队列，不承诺联系时限。
界面若直接写「已转派 / 专员已接单」，与该口径冲突。

**对策**：用「已提交转派申请 / 待专员接单」这类**未完成态**表述，不写「专员已接单」、不写时长承诺。
界面上不标「模拟」（已有约定），但答辩口径必须说清楚。

### 9.4 三层可能比 4 个 tab 更挤

三层要放摘要、诉求、用户档案、产品信息、处理依据、工单流程——**信息量其实比现在更多**，只是重新组织。若不做视觉层级，等于把 tab 换成堆叠。

**对策**：明确「演示时第一眼看什么」——上层摘要最大最显眼；中层左右分栏；处理依据与工单流程用可折叠或弱化样式。

### 9.5 表达层的输入形态限制了「真人感」

表达层现在拿到的是**成句模板**（如「已生成模拟交接工单 MOCK-xxx，尚未发送给真实客服」），只做改写，很难真的自然。

**对策**：把输入从「成句模板」改为「结构化事实 + 必须保留的关键词」，让模型自己组织语言；约束仍是「不得新增事实、不得承诺时限」。这一条建议与本次改造一并做，否则「真人感」只能到一半。
