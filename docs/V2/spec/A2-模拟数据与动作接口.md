### `users.json` 结构

```json
{
  "user_id": "U-1001",
  "name": "王先生",
  "tier": "金卡",
  "joined": "2023-04-12",
  "orders_count": 6,
  "tickets_count": 2,
  "complaints_count": 0,
  "region": "US",
  "note": "历史均为质量类问题，无恶意投诉记录"
}
```

- 覆盖：金卡/银卡/普通各若干，含 1–2 位有投诉历史的，便于演示不同分支
- **每位 DEMO 订单的持有者必须在其中**，否则中层空着

### 动作接口

```
POST /api/chat/action
Header: X-API-Key（与现有鉴权一致）
Body:   { "conversation_id": "...", "action": "transfer_to_agent", "ticket_id": "MOCK-..." }

200: { "ok": true, "ticket": { "ticket_id": "...", "status": "transfer_requested", "dispatched": false },
       "message": "已提交转派申请" }
```

**规则**

1. `action` 走白名单，当前只允许 `transfer_to_agent`；其它值返回 400。
2. 校验工单存在且属于该 `conversation_id`，否则 404 / 403。
3. 已转派过的工单重复调用 → 返回当前状态，不报错（幂等）。
4. 状态推进到 `transfer_requested`，**`dispatched` 保持 `false`**（未对接真实队列）。
5. 工单状态要能被 `POST /api/chat/turn` 的 `state.ticket` 读到。

## 验收指标与标准

**命令**

```bash
python -m pytest tests -q
```

**必须新增的断言**

| 用例 | 断言 |
|---|---|
| 档案可查 | 每位 DEMO 订单持有者能在 `users.json` 找到，字段齐全 |
| 档案字段不编造 | 找不到用户时返回 `unknown` 标记，不返回假姓名 |
| 转派成功 | 返回 `ok=true`，`status='transfer_requested'`，`dispatched is False` |
| 幂等 | 同一工单连续转派两次，第二次不报错且状态不变 |
| 越权拒绝 | `action='refund'` 返回 400 |
| 工单不存在 | 随机 `ticket_id` 返回 404 |
| 会话不匹配 | 用别人的 `conversation_id` 返回 403 |
| 鉴权 | 未带 `X-API-Key`（当配置了 key 时）返回 401 |
| 状态可回读 | 转派后走一轮 `/api/chat/turn`，`state.ticket.status` 已更新 |

## 边界

- **不接真实客服队列**，`dispatched` 永远 `false`，不写任何时长承诺。
- 不许在接口里做退款、补偿等任何权益动作（权限锁的边界）。
- `users.json` 是**模拟数据**，不许写成"真实用户"。
- 不改现有订单字段含义，只加 `user_id`。
