# B3 · 工单流程与转派

## 目标

右侧下层做成一条**逐步点亮的工单流程时间线**，并在合适的时候给出「确认转派」动作，
让「从受理到交接」这条链在台上有画面。

## 输入依赖

- `A2-模拟数据与动作接口.md`（`POST /api/chat/action`）
- `00-契约冻结.md`（`state.ticket` 字段）

## 产出物

| 文件 | 改动 |
|---|---|
| `frontend/src/components/TicketFlow.tsx` | **新增**：时间线 + 动作按钮 |
| `frontend/src/components/HandoffTicketModal.tsx` | 复用/并入，去掉重复展示 |
| `frontend/src/api/actions.ts` 或等价处 | 调用动作接口 |
| `frontend/src/hooks/` | 动作调用后的状态刷新 |
| `frontend/src/styles.css` | 时间线与按钮样式 |

### 流程节点（按顺序点亮）

```
✅ 已受理
✅ 已定位故障
✅ 已生成工单   MOCK-58BA…
⏳ 待专员接单        [ 确认转派 ]
```

| 节点 | 点亮条件 |
|---|---|
| 已受理 | 会话开始（有任意用户消息） |
| 已定位故障 | `state.product` 或 `state.node` 存在 |
| 已生成工单 | `state.ticket.ticket_id` 存在 |
| 待专员接单 | 同上，且未转派 |
| 已提交转派申请 | `state.ticket.status === 'transfer_requested'` |

**未进入工单流程时本层整体显示「当前无工单」。**

### 动作按钮

- 仅当 `state.ticket` 存在且未转派时出现
- 点击 → `POST /api/chat/action {conversation_id, action:'transfer_to_agent', ticket_id}`
- 成功后：节点推进到「已提交转派申请」，按钮消失
- 失败：按钮恢复可点，给出**明确但简短**的提示（如「提交失败，请重试」），不假装成功

### 措辞纪律（重要）

| 允许 | 禁止 |
|---|---|
| 已提交转派申请 | 已转派 |
| 待专员接单 | 专员已接单 |
| —— | 任何时长承诺（「15 分钟内」） |

原因：工单是模拟记录，未对接真实客服队列。`docs/reviews/参赛方案审核.md` 已为此警示过一次。

## 验收指标与标准

**命令**

```bash
npm run build && node browser-check.mjs
```

**必须新增的断言**

| 项 | 标准 |
|---|---|
| 无工单态 | 无 `ticket` 时显示「当前无工单」 |
| 节点点亮 | 注入 `product` + `ticket` → 「已定位故障」「已生成工单」处于点亮态 |
| 按钮出现条件 | 有 `ticket` 且 `status !== 'transfer_requested'` 时出现；已转派则消失 |
| 点击调接口 | 点击后发出 `POST /api/chat/action`，body 含正确的 `ticket_id` 与 `action` |
| 幂等展示 | 接口返回已转派状态时，节点显示「已提交转派申请」且不报错 |
| 失败不假装 | 接口返回 500 时，不出现「已提交转派申请」，出现重试提示 |
| 措辞纪律 | 页面全文**不含**「已转派」「专员已接单」；不含 `\d+ 分钟` |
| 不发聊天消息 | 点转派按钮**不产生** `/dify-api/chat-messages` 请求 |

## 边界

- **不得写成真实派单**（见上表措辞纪律）。
- 不许把转派伪装成聊天消息发给 Dify。
- 不许在前端自行推进状态——状态以接口返回为准。
- 不许在按钮上加时长、进度百分比、"预计…"这类承诺。
